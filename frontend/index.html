마주친 버그들

비관적 락에서 시작해 낙관적 락으로 넘어가는 동안, 실제로 네 번 발을 헛디뎠다. 순서대로 기록한다.

  1. 1 비관적 락

    1차 캐시가 FOR UPDATE를 무력화시켰다

    오픈 시각 체크용으로 먼저 findById를 하고, 그다음 findByIdForUpdate로 같은 행을 다시 조회했더니 락이 걸린 SELECT가 실행조차 안 됐다.

    JPA의 findById는 영속성 컨텍스트(1차 캐시)에 이미 관리 중인 엔티티가 있으면 DB에 다시 물어보지 않고 그 인스턴스를 그대로 돌려준다. 두 번째 조회가 캐시에 막혀서, FOR UPDATE가 붙은 SELECT 자체가 나가지 않았다.

    오픈 시각 체크는 스칼라 프로젝션(findOpenAtById)으로 분리해, 애초에 엔티티를 캐시에 올리지 않도록 바꿨다.

  2. 2 낙관적 락

    유령 CouponIssue 행

    재시도 루프를 돌리는데, 이미 발급받았다는 DuplicateIssueException이 엉뚱하게 발생했다.

    재시도 전체가 트랜잭션 하나를 공유했다. flush 없이 save()만 하면 실제 UPDATE가 커밋 시점까지 미뤄지는데, 그 사이 실패할 시도의 CouponIssue INSERT까지 영속성 컨텍스트에 큐잉돼버렸다.

    재고 UPDATE를 CouponIssue INSERT보다 먼저 flush해서, 버전 충돌이 INSERT 실행 전에 즉시 터지도록 순서를 바꿨다.

  3. 3 낙관적 락

    stale 엔티티가 재고를 계속 부풀렸다

    재고 2개짜리 쿠폰에 스레드 2개가 동시 요청했는데, 재고가 남았는데도 세 번째 재시도에서 CouponSoldOutException이 발생했다.

    재시도가 같은 트랜잭션(같은 영속성 컨텍스트)을 공유해서, findById가 매번 같은 stale 객체를 돌려줬다. 실패한 시도가 메모리에 남긴 +1이 롤백되지 않고 계속 누적됐다.

    재시도 로직을 별도 빈(CouponIssueAttempter)으로 분리하고 REQUIRES_NEW를 적용해, 매 시도가 완전히 새 트랜잭션 + 새 영속성 컨텍스트를 갖게 했다. 유령 행 문제도 이 김에 같이 사라졌다 — 두 버그가 사실 같은 원인(트랜잭션 공유)에서 나온 증상이었다.

  4. 4 낙관적 락

    그 해결책이 만든 새 버그: 커넥션 풀 데드락

    부하테스트(500 req/s)를 돌리자 거의 모든 요청이 30초 타임아웃으로 실패했다. HikariPool 로그에 active=10, waiting=198.

    재시도 루프를 감싸던 @Transactional이 커넥션 1개를 쥔 채로, 그 안의 REQUIRES_NEW 메서드가 또 다른 커넥션을 요구했다. 동시 요청이 풀 크기의 절반을 넘는 순간, 모든 요청이 서로의 두 번째 커넥션을 기다리는 순환 대기에 빠졌다.

    재시도 루프 자체엔 DB 작업이 없다는 걸 확인하고 @Transactional을 아예 제거했다. 이제 매 시도가 커넥션을 짧게 빌렸다가 바로 반납한다.

갈림길

버그를 고칠 방법이 하나만 있었던 건 아니다. 검토했던 대안과, 그중 하나를 고른 이유.

stale 엔티티 문제를 어떻게 없앨 것인가

  • refresh() / detach() — MySQL REPEATABLE READ 스냅샷 때문에 실제로는 안 통함(실측으로 확인)

  • refresh(PESSIMISTIC_READ) — 통하긴 하지만 '낙관적 락'이라는 이름 아래 실제로는 락을 쓰는 모순

  • REQUIRES_NEW로 매 시도를 새 트랜잭션에서 실행 — 원인(트랜잭션 공유) 자체를 제거, 최종 선택

stale 엔티티 버그와 유령 행 버그는 사실 같은 원인에서 나온 두 증상이었다. 증상 하나씩 패치하는 대신, 원인 자체를 없애는 쪽을 택했다.

분산 락을 무엇으로 구현할 것인가

  • 직접 SETNX 구현 — 안전한 락 해제, TTL 자동 갱신(watchdog)을 직접 재구현해야 함

  • Redisson — 이미 검증된 락 구현체, 최종 선택

이 프로젝트의 목적은 '락 전략 비교'지 'Redis 프로토콜 재구현'이 아니다. 비관적/낙관적 락도 프레임워크가 제공하는 기능(FOR UPDATE, @Version)을 썼지 락을 직접 구현하지 않았다.
