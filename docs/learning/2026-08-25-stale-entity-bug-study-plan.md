# 오늘의 학습 계획 (180분, 50/10 사이클 3회)

오늘 목표는 어제 발생한 findById가 엔티티를 재사용해 발생하는 문제와, 어제 다 하지 못한 GA에 대해 이해하는 것이다.

## GQ 목록

GQ1. 현재 프로젝트에서 낙관적 락 코드의 버그는 무엇일까? 그걸 해결하는 방법은 무엇일까? (오늘은 어제 미해결로 남긴 findById stale 엔티티 문제에 한정)
GQ2. 스프링에서 낙관적 락은 어떻게 동작할까? (오늘은 영속성 컨텍스트/1차 캐시가 findById와 어떻게 상호작용하는지에 집중)
GQ3. 어제 버그(들)는 왜 지금까지 발견되지 않았을까? — 테스트 커버리지 부재인가, 동시성 재현 자체가 어려워서인가?
GQ4 (제안). entityManager.refresh() / clear() / detach()는 각각 뭐가 다르고, 이 버그엔 어떤 걸 써야 할까?

## 사이클별 시간 배분

0~50분: GA1 (이어서) — 어제 로그로 확인한 stale 엔티티 증상(identityHash/version 안 바뀜) 복기, "왜 이런 일이 생기는가"를 자기 언어로 다시 설명해보기
→ 목표: GQ1의 "버그가 정확히 뭔지" 파트를 스스로 명확한 문장으로 정리

(10분 휴식)

50~100분(누적): GA2 — 공식문서 학습: JPA EntityManager.find()가 1차 캐시를 우선 확인하는 동작, refresh()/clear()/detach()의 차이, MySQL 자체엔 낙관적 락이 없고 ORM 레이어(@Version)에서 구현된다는 원리
→ 목표: GQ2 답 + GQ4에 대한 가설 세우기

(10분 휴식)

100~150분(누적): GA3 — 학습한 API로 실제 해결 시도. 재시도 루프의 findById 직전에 무언가를 추가해서 최신 데이터를 강제로 읽어오게 만들기 → 실제 스레드로 재검증
→ 목표: GQ1의 "해결법" 파트 완성

150~180분: GQ3/GA4 — 오늘 배운 것 + 고친 것 Notion에 기록 + GQ3(왜 지금까지 안 잡혔나) 성찰, 다음에 볼 GQ 하나 남겨두기
→ 목표: 학습 정리 + 재발 방지 기록화

## GA별 AI(Claude)의 역할

**GA1 — 문제 복기**
- 코드를 같이 읽으며 놓치기 쉬운 지점(1차 캐시, 영속성 컨텍스트의 범위 등)을 질문으로 짚어주기
- "이 findById가 같은 트랜잭션 안에서 몇 번째 호출이야?" 식으로 유도
- 어제 남긴 identityHash/version 로그를 같이 다시 읽으며 패턴 확인하도록 질문 던지기

**GA2 — 공식문서 학습**
- 공식문서(Hibernate Persistence Context, EntityManager API, Spring Data JPA 레퍼런스) 링크 찾아주기
- 이해한 내용을 사용자가 먼저 설명하게 하고, 틀린 부분만 짚어줌
- refresh()/clear()/detach() 차이를 표로 정리하도록 유도(직접 채우게 함)

**GA3 — 해결 시도 + 재검증**
- 사용자가 먼저 코드를 짜고, AI는 리뷰·피드백만(직접 대신 짜주지 않음)
- 재현 테스트로 실제 고쳐졌는지 같이 검증, 놓친 엣지케이스 발견
- 실제 스레드 테스트 결과(성공/실패 분포) 해석 도와주기

**GQ3/GA4 — 왜 안 잡혔나 + 정리**
- 정답 대신 "이 QA 관점에서 뭐가 빠졌을까?"라고 되묻기
- 테스트 커버리지 체크리스트 관점(단위 vs 통합, mock vs 실제 DB) 제시
- Notion 기록 구조 제안, 사용자가 쓴 초안 리뷰해서 빠진 정보 짚어주기
