# 오늘의 학습 계획 (180분, 50/10 사이클 3회)

오늘 목표는 분산 환경과 분산 락을 학습하는 것이다. 모놀리식(서버 1대)만 다뤄봐서, 여러 서버가 동시에 뜨는 상황부터 확인이 필요했다. 《가상 면접 사례로 배우는 대규모 시스템 설계 기초》와 함께 보면 좋을 듯.

## GQ 목록

GQ1. 여러 개의 서버 인스턴스가 동시에 떠 있는 분산 환경에서는, 지금까지 이 프로젝트에서 썼던 DB 트랜잭션 기반 락(비관적 락 `FOR UPDATE`, 낙관적 락 `@Version`)만으로 왜 부족해지는 상황이 생길 수 있을까?
GQ2 (제안, 1사이클 후 확정). 분산 락은 실제로 어떤 메커니즘으로 동작하며, Redisson 같은 라이브러리는 직접 구현(SETNX)에 비해 어떤 문제를 보완해주는가?
GQ3 (제안, 2사이클 후 확정). 이 프로젝트(coffee-coupon-api)에 분산 락을 적용한다면 Redisson과 직접 구현한 SETNX 중 어느 쪽이 더 적합할까, 그리고 그 이유는?

## 사이클별 시간 배분

0~50분: GA1 — 분산 환경 체감. coffee-coupon-api를 포트 두 개(8080/8081)로 동시에 띄운다고 가정하고, 둘 사이에 뭐가 공유되고 안 되는지 직접 나열해본다. 이어서 《가상 면접 사례로 배우는 대규모 시스템 설계 기초》(또는 웹 검색)에서 분산 시스템/합의(consensus)/락 관련 절을 20분 정도 읽고, DB 락이 여전히 유효한 경우 / 안 되는 경우 / 이 프로젝트는 어디에 해당하는지를 노션에 정리한다.
→ 목표: GQ1에 대한 자기 나름의 답을 2~3문장으로 정리

(10분 휴식)

50~100분(누적): GA2 — 분산 락의 실제 메커니즘 조사. SETNX/TTL 기본형, Redlock 알고리즘, Redisson이 보완해주는 것(watchdog, 다양한 락 타입) 등을 공식 문서 기반으로 조사한다.
→ 목표: GQ2 답 정리

(10분 휴식)

100~150분(누적): GA3 — 이 프로젝트(`feature/coupon-issue-distributed-lock` 브랜치)에 실제 적용. Redisson vs 직접 SETNX 결정, 설계 스펙 초안 작성.
→ 목표: GQ3 답 + 설계 스펙 초안

150~180분: 정리 — 오늘 배운 것 노션에 기록.

## GA별 AI(Claude)의 역할

**GA1 — 분산 환경 체감**
- 소크라테스식: 직접 답을 주지 않고, 서버 두 개를 띄운다고 가정했을 때 공유/비공유 자원을 스스로 나열하도록 유도
- 인메모리 락 vs DB 락(비관적/낙관적)이 서버가 여러 대일 때 어떻게 다르게 동작하는지 힌트로 유도
- 막히면 힌트 2단계(성능/자원 관점, 범위 관점)로 나눠서 제공

**GA2 — 메커니즘 조사**
- 레퍼런스 조사 위주라 직접 답변으로 진행 (공식 문서 인용 포함, 소크라테스식 아님)

**GA3 — 프로젝트 적용**
- 브레인스토밍 방식: 질문 하나씩 던지며 설계 결정을 함께 좁혀감
- 코드 작성이나 파일 생성 등 실제 구현은 설계에 대한 명시적 승인 전엔 하지 않음
