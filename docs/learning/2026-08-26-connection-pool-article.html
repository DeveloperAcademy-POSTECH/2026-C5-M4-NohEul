coffee-coupon-api · 분산 락 학습

커넥션 풀의 함정

비관적 락도, 낙관적 락도 서버가 몇 대든 정확하게 작동한다. 그런데도 분산 락이 필요한 이유는, 정확성이 아니라 전혀 다른 곳에 있다.

쿠폰 발급 프로젝트에 비관적 락(FOR UPDATE)과 낙관적 락(@Version)을 차례로 구현하고 나면 자연스럽게 이런 질문이 떠오른다. 이 두 락 모두 서버가 몇 대이든 상관없이 정확하게 동작한다는 걸 이미 확인했는데, 그렇다면 분산 락(Redis)은 대체 왜 필요한가?

1정확성은 이미 보장돼 있다

@Version은 JVM 메모리가 아니라 DB row의 컬럼이고, 버전 충돌 체크(UPDATE ... WHERE version = ?)도 DB 안에서 일어난다. 서버가 몇 대든 결국 같은 row를 보는 이상 결과는 동일하다. FOR UPDATE도 마찬가지로 DB가 직접 거는 락이라 서버 대수와 무관하다.

즉 "여러 서버가 동시에 쓰기 때문에 데이터가 꼬인다"는 걱정은, DB 트랜잭션 락만으로 이미 해결되어 있다. 분산 락을 붙이는 진짜 이유는 다른 데 있다.

2진짜 이유 — 자원 격리

비관적 락에서 충돌한 요청은 SELECT ... FOR UPDATE가 리턴할 때까지 DB 커넥션을 붙잡은 채로 대기한다. 재고 1개짜리 인기 쿠폰에 1,000명이 동시에 몰리면, 999명이 커넥션 풀(기본 10개)의 빈자리를 놓고 계속 대기하며 풀을 고갈시킨다.

1,000명이 동시에 요청했을 때
동시 요청 1,000개
↓
DB 커넥션 풀 (10개)
10개 전부 점유됨 — 990명은 락 대기 중, 각자 커넥션 하나씩 붙든 채
↓
GET /coupons/{id}
이 쿠폰과 무관한 조회 요청인데도, 남은 커넥션이 없어서 함께 막힘
원인
락 자체가 아니라 커넥션 풀 고갈 — 애플리케이션 전체가 공유하는 자원
↓
DB 락의 대기
DB 커넥션을 붙잡은 채로 대기
→ 커넥션 풀 소모
vs
Redis 락의 대기
완전히 별도 자원에서 대기
→ DB 커넥션 풀에 영향 없음

Redis 기반 분산 락은 이 "대기"를 DB가 아니라 완전히 별도의 저장소(Redis)에서 처리한다. 아무리 많은 요청이 락을 기다려도, DB 커넥션 풀에는 영향이 없다. 즉 비관적 락은 정확성은 보장하지만, 그 대가로 애플리케이션 전체가 공유하는 자원을 소모시킨다 — 분산 락은 그 대가를 없앤다.

3또 다른 이유 — 범위

지금까지 만든 락(FOR UPDATE, @Version)은 전부 DB의 특정 row를 두고 경쟁할 때 쓰는 도구다. 그런데 "여러 서버 중 하나만 배치 작업을 실행해야 한다" 같은 경우엔, 지키려는 대상이 row가 아니라 실행 권한이다 — 애초에 잠글 데이터가 없다.

데이터 보호 (이 프로젝트)

  • 잠글 대상이 명확함 — 쿠폰 재고라는 실제 row
  • FOR UPDATE / @Version으로 충분

실행 권한 보호 (예: 배치 작업)

  • 잠글 데이터가 없음 — N대 중 누가 실행할지만 결정하면 됨
  • Redis 락이나 MySQL GET_LOCK() 같은 별도 도구 필요

4정리

이 프로젝트에서 분산 락을 붙이려는 진짜 동기는 2번(자원 격리)이다. 3번(배치 작업 실행 조율)은 이 프로젝트에 아직 존재하지 않는 시나리오라, "분산 락이 필요한 또 다른 이유도 있다"는 걸 보여주는 참고 사례에 가깝다.
