# 락 전략 비교용 k6 부하테스트 하네스 설계

- 날짜: 2026-08-17
- 브랜치: `feature/lock-strategy-load-test`
- 목적: **락 없음(대조군)** 포함 네 가지 — 락 없음/비관적/낙관적/분산 락 — 이 가정한 트래픽 규모(peak 6,000 QPS)에서 실제로 과발급이 나는지/안 나는지, 동일한 기준·동일한 도구로 반복 검증할 수 있는 외부 부하테스트 하네스(k6)를 만든다.

## 범위

- 이번 스펙은 **하네스(스크립트 + 러너북) 자체의 설계**다. 낙관적 락, 분산 락 구현은 범위 밖 — 각각 별도 브랜치·스펙에서 다룬다. 비관적 락은 이미 구현돼 있어 이 하네스로 바로 검증 가능하다.
- **락 없음은 첫 번째 비교 대상(대조군)** 이다 — 6,000 QPS에서 과발급이 실제로 얼마나 심한지 정량적으로 보여주는 기준선 역할을 한다.
- **비교 방식은 브랜치 전환이 아니라 엔드포인트 전환이다.** 네 전략은 각각 `POST /api/coupons/{campaignId}/issue-<전략>`(`issue-no-lock`/`issue-pessimistic`/`issue-optimistic`/`issue-distributed`)이라는 별도 엔드포인트로 구현된다. 각 전략은 자기 브랜치에서 구현되지만, 브랜치가 순차적으로 develop에 머지되므로(구현→머지 반복) 엔드포인트가 계속 누적된다 — 그래서 비교 시점에는 이미 여러(또는 전부) 엔드포인트가 한 앱 안에 같이 떠 있고, 하네스는 브랜치를 바꿀 필요 없이 `STRATEGY` 값만 바꿔서 반복하면 된다.
  - 기존에 이미 병합된 비관적 락은 접미사 없는 `/issue`를 그대로 쓰고 있다. `/issue-pessimistic`으로 이름을 맞추고 `/issue-no-lock`을 새로 추가하는 작업(`CouponService`에 `findById` 기반 락 없음 메서드 추가 + 컨트롤러에 두 엔드포인트 매핑)이 선행돼야 한다. 이 작업은 이 하네스 구현 계획의 범위 밖 — 낙관적/분산 락 엔드포인트 추가와 마찬가지로 각자 별도 브랜치/작업으로 진행한다.
- 판정 기준은 **정합성(과발급 여부)만**이다. k6가 기본으로 뽑아주는 처리량(req/s)·지연시간(p95 등)은 결과 기록에는 남기되, 이번 단계의 통과/실패 기준에는 쓰지 않는다 — 나중에 처리량/지연시간 비교로 넘어갈 때 재작업 없이 쓰기 위한 사전 준비다.
- 오픈 시각(`openAt`) 경계 자체의 타이밍 재현은 범위 밖(이미 `CouponServiceTest`/`GlobalExceptionHandlerTest`가 다룸). 이 하네스는 **이미 오픈된 캠페인**만 대상으로 한다.
- CI 자동화는 범위 밖. 사람이 `STRATEGY` 값을 바꿔가며 수동으로 실행하는 러너북으로 제공한다.
- 캠페인 생성 API는 이 프로젝트에 없다(의도적으로 범위 밖). 따라서 시드(seed)는 API가 아니라 **SQL 스크립트로 직접 캠페인 행을 insert**하는 방식으로 처리한다.

## 1. 용량 산정 (가정)

브레인스토밍 과정에서 합의한 가정치:

| 가정 항목 | 값 |
|---|---|
| 알림 대상(중규모 프랜차이즈) | 300,000명 |
| 캠페인 발급 수량 | 2,000장 |
| 알림 대비 실제 시도 비율 | 20% (60,000명) |
| 오픈 직후 몰림 윈도우 | 10초 |
| **Peak QPS** | **≈ 6,000** |

재시도로 인한 QPS 증폭(사용자가 실패 후 재요청)은 이번 하네스의 부하 프로파일에는 반영하지 않는다 — 60,000건은 "순수 최초 시도"만 가정한 숫자이며, 이 캡을 명시적으로 남겨 나중에 필요하면 배수 계수를 곱해 확장할 수 있게 한다.

**로컬 실행 기본값(RATE=500)과의 관계**: 위 표의 6,000 QPS는 이 시스템이 감당해야 한다고 가정한 설계 목표치이고, `coupon-issue-scale.js`의 `RATE` 기본값은 500이다. 이 둘은 의도적으로 다르다 — 로컬 단일 인스턴스(HikariCP 풀 10개, k6와 앱과 DB가 같은 장비를 공유)에서는 6,000 QPS를 걸면 락 전략 자체의 차이보다 커넥션 풀/장비 포화가 결과를 지배한다(4번 섹션 참고). 500 QPS만으로도 no-lock 과발급 재현과 전략 간 상대 비교라는 이 하네스의 목적은 충분히 달성됨이 실측으로 확인됐다(2026-08-20, no-lock 재고 2,000장 중 1,582장 과발급 재현). 6,000은 실서버/CI 환경에서 절대 처리량을 검증할 때 `-e RATE=6000`으로 명시적으로 올려서 쓴다. 즉 500을 "새로운 설계 목표치"로 격상한 게 아니라, "로컬에서 이 목적을 달성하는 데 필요한 최소 실행 규모"로 별도 기록해둔 것이다.

## 2. 컴포넌트

`coffee-coupon-api/load-test/` 디렉토리를 새로 만들고, Kotlin 소스 트리와 분리해서 관리한다(JS/SQL/셸 스크립트라 `src/main`, `src/test`에 넣을 이유가 없음).

| 파일 | 역할 |
|---|---|
| `seed.sql` | `CouponTemplate` 1건 + `CouponCampaign` 1건(재고 2,000, `openAt`은 과거)을 insert하고 `SELECT LAST_INSERT_ID()`로 생성된 campaign id를 출력 |
| `coupon-issue-scale.js` | k6 스크립트. `constant-arrival-rate` executor로 `RATE`(기본 500, 로컬 실행 기본값) req/s를 10초간 `POST /api/coupons/{campaignId}/issue-{STRATEGY}`에 발사. 설계 목표치인 6,000 req/s로 돌리려면 `-e RATE=6000` (1번 섹션 참고) |
| `verify.sh` | 부하 종료 후 `GET /api/coupons/{campaignId}`를 호출해 최종 재고/발급 수량을 조회하고, k6 요약과 대조 |
| `README.md` | 전략별 실행 순서를 적은 러너북 |

### userId 유일성

`CouponIssue`에는 `(couponCampaignId, userId)` 유니크 제약이 있다. 60,000건의 요청이 서로 다른 `userId`를 쓰지 않으면 "재고 소진"이 아니라 "중복 발급"(다른 에러 코드)으로 판정이 오염된다. k6 스크립트는 `exec.scenario.iterationInTest`(전역적으로 유일한 반복 카운터)를 기반으로 `userId`를 생성해 전체 실행에서 중복이 없도록 한다.

## 3. 데이터 흐름 (한 번의 비교 실행)

```
0. (한 번만) 엔드포인트가 다 모여 있는 브랜치를 체크아웃하고 ./gradlew bootRun 으로 앱 기동 (로컬 MySQL 대상)
1. 검증할 STRATEGY 선택 (no-lock / pessimistic / optimistic / distributed)
2. mysql < load-test/seed.sql 실행 → campaign id 획득 (예: 42)
3. k6 run load-test/coupon-issue-scale.js -e CAMPAIGN_ID=42 -e STRATEGY=<선택한 전략>
   → 500 req/s(로컬 기본값) × 10초, 총 5,000건을 /api/coupons/42/issue-<전략>에 발사, 각 요청 고유 userId
   → 설계 목표치(6,000 req/s)로 돌리려면 -e RATE=6000 추가
   → k6 요약에 상태코드별 카운트(200/403/409/5xx), 처리량, p95 등이 남는다
4. ./load-test/verify.sh 42 실행
   → GET /api/coupons/42 로 최종 remainingQuantity/issuedQuantity 조회
   → k6의 200 카운트와 issuedQuantity가 일치하는지, remainingQuantity == 0 인지 확인
5. 결과를 비교 문서에 기록 (성공 카운트, 최종 발급 수량, 에러 코드 분포, 참고용 처리량/지연시간)
```

1~5번을 STRATEGY만 바꿔서 no-lock(대조군) → 비관적 → 낙관적 → 분산 순으로 반복한다. 앱을 한 번만 띄워두면 되므로(엔드포인트 전환이지 브랜치 전환이 아니므로), 자동화하지 않고 사람이 따라 하는 러너북이라도 반복 부담이 적다.

## 4. 에러 처리 / 알려진 한계

- **DB 커넥션 풀**: Hikari 기본 풀 크기가 작아서(기본값), 실제 처리량은 6,000 QPS에 못 미칠 수 있다. 이건 네 가지 모두에 동일하게 적용되는 조건이라 상대 비교에는 문제가 없지만, 절대 수치를 해석할 때는 "락 자체의 한계"와 "커넥션 풀의 한계"를 구분해서 기록한다. 로컬 실행 기본값을 500으로 낮춘 것도 같은 이유다 — 6,000을 로컬에서 그대로 걸면 이 구분 자체가 불가능해진다(1번 섹션 참고).
- **5xx 응답**: 락 경합과 무관한 인프라 오류(커넥션 타임아웃 등)로 5xx가 나오면 이는 정합성 판정과 별개로 기록만 하고, 성공/실패 카운트 정합성 검증에서는 5xx를 "미확정"으로 분리해 200/403/409와 섞지 않는다.
- **낙관적 락의 재시도 여부**: 낙관적 락 구현 시 충돌 재시도를 넣을지는 그 브랜치의 구현 태스크에서 결정한다. 이 하네스는 재시도 유무와 무관하게 동일한 방식(최종 재고/성공 카운트 대조)으로 결과를 측정한다 — 재시도가 없으면 성공 카운트가 2,000에 못 미칠 수 있는데, 이는 과발급이 아니라 "언더셀"로 결과에 별도 기록한다.

## 5. 테스트 (하네스 자체의 검증)

이 하네스는 프로덕션 코드가 아니라 테스트 도구이므로 별도의 자동 테스트 스위트는 두지 않는다. 대신 `README.md`에 "이 하네스가 올바르게 동작하는지" 확인하는 절차를 남긴다:

- `seed.sql`을 두 번 연속 실행해도 매번 새 campaign id가 발급되는지 (테이블을 지우지 않고 insert만 하므로 이전 실행과 섞이지 않는지) 확인
- 아주 작은 스케일(예: 재고 10, 총 시도 100)로 먼저 실행해 스크립트 자체의 정확성을 검증한 뒤, 로컬 기본값인 500 QPS로 실행한다. 6,000 QPS(설계 목표치) 풀 스케일은 실서버/CI 환경에서만 의미가 있고, 로컬 단일 인스턴스에서는 생략해도 된다(1번 섹션 참고)

## 결정된 사항 요약 (브레인스토밍 과정에서 확정)

- 비교 대상: **락 없음(대조군, 첫 번째) → 비관적 락 → 낙관적 락 → 분산 락** 네 가지. 네 전략은 브랜치가 아니라 **엔드포인트**(`issue-no-lock`/`issue-pessimistic`/`issue-optimistic`/`issue-distributed`)로 구분되고, 브랜치가 순차 머지되면서 한 앱 안에 누적된다. 락 없음은 옛 baseline 브랜치를 재사용하지 않고 현재 스키마 위에 `findById`로 락만 제거한 새 엔드포인트로 추가한다
- 용량 산정: 알림 대상 30만 명, 재고 2,000장, 시도 비율 20%, 몰림 윈도우 10초 → peak 6,000 QPS
- 판정 기준: 정합성(과발급 여부)만. 처리량/지연시간은 기록만 하고 이번 판정에는 미사용
- 부하 도구: k6 (Gatling 대비 JVM/Gradle과 무관해 프로젝트 빌드에 영향 없음, arrival-rate 모델이 QPS 시나리오 표현에 직관적)
- 실행 방식: 브랜치 전환이 아니라 `STRATEGY` 값 전환으로 비교(엔드포인트가 한 앱에 누적되므로). CI 자동화는 범위 밖
- 시드 방식: 캠페인 생성 API가 없으므로 SQL 직접 insert (`load-test/seed.sql`)
- (기각안) JVM 내부 `ExecutorService` 기반 확장 테스트(`@Tag("scale")`) — 정합성만 볼 때는 더 저렴했지만, 처리량/지연시간을 나중에 같이 보고 싶다는 요구 때문에 k6 기반 외부 부하테스트로 대체
- (2026-08-20 추가 결정) `coupon-issue-scale.js`의 `RATE` 기본값을 6,000 → 500으로 변경. 6,000(용량 산정 결과)은 설계 목표치로 문서에 그대로 남기고, 500은 로컬 단일 인스턴스에서 이 하네스의 목적(과발급 재현, 전략 간 상대 비교)을 달성하는 데 필요한 실행 규모로 별도 채택 — 비즈니스 가정(30만 명/20%/10초)을 손대서 500을 역산해 만들어내지 않는다(근거 없는 숫자가 되므로). 실측(no-lock, 500 QPS × 10초)으로 1,582장 과발급을 재현해 목적 달성을 확인함
